# F03 qualification contract and fixture protocol

This change supplies a common, executable input and observation contract for the F04 Hubs/Spoke and F05 Babylon/VRSpace evaluations. It does not select a foundation, instantiate a production runtime, implement a service, or claim device acceptance. F06 owns the foundation decision. The packages remain usable without a conference application or account.

## Run and integration

```sh
npm ci --ignore-scripts
npm run build
npm run generate --workspace @browser-vr-engine/qualification-fixtures
npm run check
npm run example:fixtures
```

The reproducibility check is part of the fixture workspace's tests. Generate only when intentionally updating inputs; regular CI uses `check:fixtures` to catch drift. Tests use Node's in-process test isolation so named assertions are observable even in environments that restrict child test-runner IPC. The fixture tests do not depend on process isolation. F02 remains the owner of repository-wide evidence, CI, packaging and review tooling.

The two F03 packages are version `0.1.0`. This is a provisional qualification contract. `packages/qualification-fixtures/fixtures/comparison.json` binds all comparison inputs with content hashes, including the schema export. Freeze that file and the candidate source revisions before collecting comparable runtime samples. Input, threshold or interpretation changes require a new version and a new comparison; do not tune one candidate after inspecting its results.

The adapter is deliberately small:

```ts
interface QualificationAdapter {
  readonly descriptor: { readonly id: string; readonly version: string };
  probe(): Promise<readonly CapabilityObservation[]>;
  load(world: WorldFixture, context: QualificationContext): Promise<void>;
  perform(step: ScenarioStep, context: QualificationContext): Promise<readonly AssertionObservation[]>;
  dispose(): Promise<void>;
}
```

Supply the generated world/scenario and an `AssetPort` to `runScenario`. `probe` is an explicit capability query for the evaluation harness; a probe does not satisfy scenario assertions by itself. The runner clones and deeply freezes input documents, fills absent observations as `not-run`, and calls `dispose` after load/action errors or cancellation. Candidate scene state must be a separate mutable representation. The optional `waitForTick` scheduler maps logical ticks to the harness's actual clock. Without it, the runner performs logical replay and makes no elapsed-time claim.

The checked scenario has 13 checkpoints: render, traverse the arch, select/grab/release a prop, hear the four calibrated corners, play/seek/pause wall video, edit through the actual browser authoring route, export/reload, reconnect real clients, and operate an actual headset. The final headset checkpoint is a required operator procedure. A direct assignment into a candidate's internal object does not establish a working editor, and a stored count of six emitters does not establish an audible graph.

Each result observation identifies the assertion, status, method and detail. `assessQualification` rejects stale world/scenario hashes, missing or unexpected assertions, unsupported results and disallowed evidence methods. Results must be attached to F02's reviewed evidence records together with the comparison digest, candidate revision, device/topology profile, raw measurements and artifact hashes. The result type is not a second progress ledger or an attestation of hardware truth.

## Coordinates, fixtures and ownership

Meters, right-handed axes and +Y up apply consistently to graphics, collision and audio. The identity camera/listener faces -Z; asset front is separate metadata. Quaternion order is XYZW; matrices are column-major and compose `parentWorld * local`. The mathematical fixture tests independently check Z-up centimeters, a handedness reflection, rotated hierarchy, signed scale/shear, and listener yaw. These follow the coordinate and transform conventions in the [Khronos glTF specification](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#coordinate-system-and-units) and [Web Audio listener specification](https://www.w3.org/TR/webaudio/#AudioListener).

All four model inputs are actual glTF files with embedded binary buffers. The bird has skinning, morph and animation data; it is not a substitute programmatically spawned by an adapter. The world contains the same separate box proxies for both candidate physics evaluations. This avoids a dependency on the later collider compiler and does not endorse box approximations for arbitrary imported buildings.

The source catalog contains only original synthetic resources and identifies their generator or checked media seed. Imported supplier originals and native applications are later asset-pipeline acceptance inputs. Qualification must not require committing privately licensed models to this repository, and the provenance fields must not become vendor-specific import restrictions.

## Reference workloads and thresholds

The checked `workloads.json` contains the following **desktop reference inputs**, not capacity promises:

| Profile | Real browser clients | Protocol clients | Microphone publishers |
| --- | ---: | ---: | ---: |
| `foundation-local-v1` | 1 | 0 | 0 |
| `foundation-two-client-v1` | 2 | 0 | 2 |
| `interactive-20-v1` | 2 | 18 | 2 |
| `interactive-50-v1` | 2 | 48 | 2 |
| `interactive-100-v1` | 2 | 98 | 2 |

All use the same seed and scene, 20 Hz poses/snapshots, 60 Hz simulation, one video decoder and six audio panners per real browser, a 1280 x 720 viewport at effective DPR 1, a 30 Hz desktop target, 60 seconds of warm-up and three 180-second samples. The 22-second functional scenario is a checkpoint script; it is not a 180-second camera-performance trace. A performance harness must hold or repeat a declared deterministic observer/action route for the entire sample and record that route in its frozen run profile. Protocol clients cannot count as real decoders, renderers or microphones. N12/R06 own actual load execution and N/M lanes own the services it requires.

| Check | Frozen threshold/interpretation |
| --- | --- |
| Double-precision coordinate reference | Absolute error at most 1e-6 m |
| Loaded static reference anchors | At most 1 mm error, with the readback method recorded |
| Equal-distance audio gains | At most 0.1 dB difference after isolating the corner-music bus |
| Source cutoff | Smooth fade from 10 m to 14 m; gain reaches zero at cutoff |
| Uploaded marker A/V offset | At most 80 ms after warm-up, measured from decoded picture and sound |
| Application frame intervals | p95 at most 1.1 target periods; p99 at most 2.1 periods; intervals above 1.5 periods at most 1%; annotate every stall above 250 ms |
| Cleanup | Ten load/unload cycles; candidate-owned resources return to baseline with persistent caches explained |

Physics traversal, object identity, full required-data round trips and single video-audio routing remain functional obligations even if a frame threshold passes. Report all repetitions and raw sample counts. Application frame intervals are not CPU/GPU duration or XR compositor cadence; do not add CPU/GPU work as if necessarily serial, infer reprojection from average FPS, or label an unavailable memory counter as zero.

The inverse/linear/exponential distance curves have an explicit fade envelope. Web Audio distance models alone do not guarantee zero sound at a distance cutoff; the reference math is defined separately and tested against independent answers. See [Web Audio distance models](https://www.w3.org/TR/webaudio/#distance-models).

## Device and evidence requirements

`devices.json` contains only target templates: an ordinary integrated-graphics laptop, an actual selected headset and a premium desktop. It records no observed hardware. An observed device record needs CPU, GPU, RAM, OS, browser/version, graphics backend and audio input/output. An observed headset additionally needs model, firmware, runtime and actual refresh with `physical: true`. This flag is an evidence claim that still needs underlying artifacts and review.

Use F02's run artifacts for additional concrete details: power mode, viewport/effective pixel count, per-eye render dimensions, browser channel, reference space, controller/hand features, session duration, microphone/headphone/speaker routing, service versions and network topology. Freeze a separate premium-desktop or headset workload profile before those comparisons. The desktop 30 Hz profile cannot qualify immersive VR. A headset profile must target its actually selected refresh and dimensions, for example a supported 72 or 90 Hz mode only when observed on that device. It must not inherit desktop quality numbers silently.

Minimum meaningful comparison needs two actual browser clients plus candidate services, an ordinary graphics device and one actual target headset. Audio qualification also needs headphones, speakers and a real microphone. A headless software GPU can establish browser API/render execution for that environment, but not ordinary-device graphics performance. Browser automation, synthetic poses and XR emulators cannot replace physical headset or physical audio observations.

The headset operator procedure covers user-activated session entry and denial, controller rays and UI, grab/release, seated scale, recentering, head/listener rotation, near-wall feedback while retaining real head motion, visible error dismissal and exit, sleep/resume and return to desktop. Test hands, layers and WebGPU separately. Session entry follows the actual [WebXR user activation and permission flow](https://www.w3.org/TR/webxr/#application-flow).

Audio observations include four-corner localization, continuous approach/cutoff, conversation plus video, microphone mute/stop, output-device changes and reconnect through the final playback graph. Numerical gain tests do not establish echo cancellation, output-device handling or subjective localization. M26 owns the final physical-audio gate; F04/F05 can attach observed comparisons using the same protocol.

Unperformed steps remain `blocked`, `unsupported` or `not-run` with the next needed resource identified. Do not store personal recordings, private slides, provider credentials, delivery URLs or raw identifying device/head traces merely to support these synthetic tests.

## Later ownership

W01 expands production world/prefab semantics; W02 implements lifecycle; A01/A13 implement full asset and collider pipelines; F08 implements identity/control services; N lanes implement actual authority and transport; M lanes implement final media/audio. F03 does not depend on any of them. F04/F05 map either candidate to the same inputs, and F06 retains the qualified subsystems. This permits a Hubs-based result without a preliminary Babylon rewrite.

F03-specific tests and this document establish a prepared local implementation. Acceptance, merge and release qualification remain separately recorded by the repository workflow at the reviewed commit.
